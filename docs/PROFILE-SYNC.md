# Versioned publication and safe local drafts — 2026-10-25

Incident evidence: production /profile/save and /profile/me /profile/load returned 409; UI said saved before server acceptance and mapped all 409 errors to a cross-device conflict. A corrected canonical birthdate could quarantine old encrypted profile data while the editor discarded the replacement revision. The previous SQL timestamp CAS also compared a PostgreSQL timestamp against a JS Date, losing sub-millisecond precision. The exact failed branch of any individual historical request is not recoverable from HTTP status alone.

The server now exposes an opaque SHA-256 revision for authenticated profile reads, including quarantined or missing profiles without exposing their old medical contents. A save requires that exact revision and atomically compares encrypted snapshot plus immutable identity. It never changes QR ID, never trusts client clocks, never relaxes identity checks. Public reads still fail closed and require requested-ID binding. No database migration, record deletion, billing/authenticator or encryption-key change.

The editor keeps owner-bound local drafts separate from confirmed server snapshots. Existing identity-matched local work can be reviewed and published over a quarantined old profile using a fresh revision. Only server-confirmed success creates QR artifacts or says published. Network errors, revision conflicts and refresh preserve drafts. Closing a tab stores a local draft instead of silently posting to the server. Same-account conflicting versions can be compared in a text-only table; the owner explicitly loads the published version or publishes the reviewed draft, still protected by CAS. Newer edits made during an in-flight save remain pending.

Upgrade: keep the current app session, refresh/reopen online without clearing website data or logging out, review the recovered draft and click Save and update my QR codes. If two devices hold different drafts, publish one, then compare the other before choosing. Do not fill the same medical history repeatedly or assume local-draft status means publication. A recreated account has a new QR ID; an old QR for a deleted account must be regenerated. There is no fallback to another cached patient when public verification fails.

Tests: npm test in backend; frontend node --test tests/medical-isolation.cjs tests/birthdate.cjs; profile-sync DOM tests require jsdom@26 in QA (NODE_PATH may point to a temporary QA install), then node --test tests/profile-sync-dom.cjs. Two fictional devices, wrong identity, stale/concurrent revisions, microsecond timestamp, quarantined old birthdate, first profile, full nested medical-object roundtrip, offline failure and in-flight account change are covered. Full editor/register/public-card DOM checks were also run with fictional data. Physical phone scan of the owner's corrected profile remains a user verification step; no live health profile was read or erased during this repair.

## Release 11: installed-client migration repair

Observed follow-up: screenshots still displayed the old native alert removed from the deployed form. The previous service worker served application JS cache-first by unchanged URL, allowing new HTML to execute old medical-load/save code. Tests that only inspected deployed files or fresh DOMs did not exercise that installed-worker state.

All first-party app-script URLs now carry release 11, the worker uses network-first for app/i18n code with offline cache fallback, and HTTP headers revalidate entry points/worker/code. Update registration bypasses HTTP cache and offers a manual apply button that preserves a matching draft before reloading. Cache migration touches only doctorqr CacheStorage, never local medical storage. Automatic plan/tour overlays no longer cover the medical editor; their existing buttons still open them.

For authenticated owners only, a quarantined server profile can be returned as review_profile when changing only its birthdate makes ALL other immutable identity checks and any embedded account binding pass. This is a review draft, never a public response and never automatically published. Different name/email/document/account bindings remain blocked. It can recover the previous server snapshot when an older client already cleared its local copy; unpersisted changes not present in any device/server cannot be reconstructed.

Real Chromium regression: load the actual pre-sync service worker and seed its stale unversioned JS cache, reproduce stale code delivery, migrate to the release-addressed app, recover a fictional owner review profile, publish with the real form serializer, generate and decode the actual PNG QR with jsQR, open that decoded URL in a different fictional patient's browser context, and verify offline draft retention without fake success. Source: tests/installed-update-browser.cjs; run from frontend root with Playwright, jsqr@1.4, pngjs and a Chromium executable (PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH). The old worker fixture is source code only.
